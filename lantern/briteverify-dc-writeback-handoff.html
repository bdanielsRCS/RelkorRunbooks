BriteVerify → Data Cloud Writeback

End-to-end refactor of the BriteVerify email-verification writeback flow into Salesforce Data Cloud, replacing v1's hardcoded credentials and broken auth path with Custom-Metadata-driven configuration and the proper a360 token exchange.

Org · latStag ✓ End-to-end validated 2026-04-28 Author · Relkor Cloud Solutions
✅
Status: Smoke-tested end-to-end in latStag on 2026-04-28. Writeback flows from Apex → Ingestion API → raw DMO → Identity Resolution → unified DMO with IsVerified=true rolled up onto the merged record. The 7-hour LOE estimate was accurate.

What was built

A refactored Apex invocable action (BriteVerifyFlowAction_v2) that verifies an email via BriteVerify and writes the verification status back to the Salesforce Data Cloud ssot__ContactPointEmail__dlm DMO via the Ingestion API. Designed to be called from a Data-Cloud-triggered Flow.

Architecture

Flow at runtime

Data Cloud Triggered Flow (on ssot__ContactPointEmail__dlm change)
   │
   │   passes 3 inputs:
   │     emailAddress    = $Record.ssot__EmailAddress__c
   │     emailAddressKey = $Record.ssot__Id__c          ← composite key (e.g. "sbtest8preferredEmail")
   │     partyId         = $Record.ssot__PartyId__c     ← e.g. "sbtest8"
   │
   ▼
BriteVerifyFlowAction_v2.verifyEmails(...)
   │
   ├─► Reads BriteVerify_Settings__mdt.getInstance('Default')
   │
   ├─► Step 1 — SF OAuth client_credentials → core access_token
   │      POST {OAuth_Token_URL__c}
   │
   ├─► Step 2 — a360 token exchange → DC access_token + DC instance_url
   │      POST {OAuth_Token_Exchange_URL__c}
   │      grant_type=urn:salesforce:grant-type:external:cdp
   │
   ├─► Step 3 — Call BriteVerify
   │      GET {API_Endpoint__c}/emails.json?address=...&apikey=...
   │
   └─► Step 4 — POST to Data Cloud Ingestion API
          POST {DC_instance_url}/api/v1/ingest/sources/{Source}/{Object}
          body: { "data": [ { EmailAddressKey, EmailAddress, PartyId, IsVerified, ... } ] }
          response: 202 Accepted
   │
   ▼
Row lands in BriteVerify DLO   →   Identity Resolution merges into
                                    UnifiedssotContactPointEmailNew__dlm
                                    where IsVerified=true rolls up onto
                                    the merged record for that email/party.

Where Marketing Cloud reads from

Confirmed via MarketSegmentActivation metadata: the existing test activation TEST_DataBricks_members reads from UnifiedssotIndividualNew__dlm (the unified Individual DMO). Production activations targeting MC should follow the same pattern — read from unified DMOs, not raw — so the writeback's IsVerified=true reaches MC after Identity Resolution runs.

⚠️ Activation gap: TEST_DataBricks_members has empty ActivationObjectPath, meaning it doesn't currently traverse to ContactPointEmail. For MC to filter on IsVerified, an activation that exposes the email entity (or includes it in the related-object path) needs to exist. This is outside the scope of this writeback work but should be on someone's radar before go-live.

Deploying to a new environment (UAT, prod, etc.)

  1. Deploy the codebase: ConnectedApp + Apex classes + Custom Metadata fields + the placeholder Default record.
  2. Configure the Connected App in the target org:
    • Setup → App Manager → Lantern_DC_Ingestion → Manage
    • Edit Policies → set Run-As user (a dedicated integration user with Data Cloud admin), Permitted Users = Admin approved, IP Relaxation = Relax
    • Manage Profiles or Manage Permission Sets → authorize a profile/permset the Run-As user has
    • Manage Consumer Details → copy Consumer Key + Consumer Secret
  3. Populate BriteVerify_Settings.Default via Setup → Custom Metadata Types with the values above.
  4. Verify the Ingestion API source BriteVerify_Verification_Results exists in the target Data Cloud workspace and is mapped to ssot__ContactPointEmail__dlm. If not, recreate using the OpenAPI spec.
  5. Smoke test via Apex anonymous (sample below) → expect success=true, ingestionSuccess=true, HTTP 202.
  6. Trigger Identity Resolution to merge the writeback into the unified DMO: Setup → Data Cloud → Identity Resolutions → Unified Individuals → Run Now.

What's deliberately left as v1 (not yet retired)

  • BriteVerifyFlowAction.cls (the old version with hardcoded credentials and no token exchange) — still in the codebase, still active. Once v2 is wired into the upstream flow and validated in UAT, v1 can be removed.
  • BriteVerifyEmailVerification.cls — Layer 2 (CRM-side) — uses BriteVerify_Settings__mdt correctly already; no changes needed.
  • BriteVerifyController.cls — Layer 1 (LWC controller) — still has hardcoded API key. Out of scope for this work; flag for follow-up.

Wiring the upstream Flow to v2

The existing BriteVerify_Email_Verification_Flow.flow-meta.xml calls BriteVerifyFlowAction (v1). To switch to v2:

  1. Open the flow in Flow Builder
  2. Find the Call_BriteVerify_API action node
  3. Change the Apex Action dropdown from BriteVerifyFlowAction → Verify Email via BriteVerify (v2)
  4. Update the input mapping to pass:
    • emailAddress ← varEmailAddress (existing)
    • emailAddressKey ← NEW — wire to varEmailAddressKey (which the upstream trigger should populate from $Record.ssot__Id__c)
    • partyId ← varPartyId (existing)
  5. Add a filter on the trigger to fire only when Email_Type__c = 'preferredEmail' AND ssot__IsVerified__c = null (avoids re-verifying on every change).
  6. Save + Activate.

Tests

BriteVerifyFlowAction_v2Test.cls covers:

  • Settings-disabled / settings-not-found path
  • Input validation (missing required fields)
  • Batch input → batch output
  • BriteVerify HTTP error path

⚠️ Custom Metadata records can't be inserted in test classes, so the happy path can't be fully exercised in unit tests. The smoke-test snippet above is the runtime validation.

Known limitations / follow-ups

  1. Custom Metadata stores OAuth_Client_Secret__c in plaintext. Migrating to a Named Credential + External Credential would be the proper Salesforce pattern. Out of scope for this LOE; ~3h additional work.
  2. No auto-retry on transient failures. A single 5xx from the Ingestion API → flow run reports failure. Consider wrapping in a retry / dead-letter pattern if call volume grows.
  3. Token caching not implemented. Each invocation acquires a fresh DC token (2 callouts). For high-throughput scenarios, cache the token in Cache.Org partitioned by client_id and reuse until near expiry.
  4. BriteVerifyController.cls still hardcodes API key — separate cleanup needed before that class deploys to prod.
  5. Activation gap (see above) — needs UnifiedssotContactPointEmailNew__dlm exposed in an MC-bound activation for IsVerified to surface to Marketing Cloud.
