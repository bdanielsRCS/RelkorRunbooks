The headline change: Release 3 introduces Accounts Receivable Recovery (ARR) as a new line of business in the same Salesforce org as Zero Balance (ZB). ARR teams work client-isolated encounters (Christus Health, Northwestern Medicine), with their own queues, list views, status codes, and routing — all without disturbing the existing ZB workflow.

Changes by who you are 5

📋 If you're an ARR Collector or Auditor

A new workspace for Accounts Receivable Recovery encounters — client-aware, with cleaner data and built-in guardrails.

  • You'll only see your client's encounters. Christus team sees Christus encounters; Northwestern team sees Northwestern. No cross-client noise.
  • New status codes: "ARR - Offshore Adjustment Review", "ARR - Sent to Coding". Each one routes the encounter to the right queue automatically when you save.
  • New ARR-specific Adjustment Reasons: "Denial - Max Units Exceeded (MUE)", "Denial - Bundling", "Contractual Adjustment - Contractual Variance".
  • New imported-data fields visible on each encounter: Placement Date, Client Epic Work Queue, Imported Payor names + balances for Primary, Secondary, and Tertiary payors.
  • Encounter Payor records now show net balance and financial class automatically — no manual math required.
  • Cleaner Root Cause picklist: only Root Causes that apply to ARR are selectable on ARR encounters. ZB-only Root Causes won't accidentally show up.
  • The old xD - * proof-of-concept fields have been retired. The replacement fields (Imported Payor balances) provide the same info more cleanly.

🔍 If you're a ZB Auditor

Your day-to-day is largely unchanged — Release 3 was about adding ARR alongside, not modifying ZB.

  • Your encounters, queues, and list views look the same. Sharing rules, permissions, and status codes for ZB are unchanged.
  • One small enhancement: the encounter highlights at the top of every record now show the Titan Net Balance.
  • Smarter Payor lookup: when adding an Encounter Payor, only Payor accounts appear in the picker — no more accidentally picking a hospital client.
  • If you also work some ARR encounters, you'll see ARR-specific options on those records (status codes, root causes, adjustment reasons). They won't show on ZB encounters.

👥 If you're a Supervisor (ARR or ZB)

A few new tools for triage and routing, plus stronger guardrails on data integrity.

  • New queue: "ARR - Offshore Adjustment Review" — supervisors at NWM are members. Encounters with that status auto-route here for review.
  • Triage flow for new ARR encounters: "Newly Unassigned" encounters are visible only to client supervisors until you assign them out, so they don't get worked accidentally before triage.
  • Contingency rate caps are now enforced automatically on ARR Payment activities for clients with split commission. The system will adjust the rate to land at the cap, then zero out further payments — no manual cap-tracking required.
  • "Log Follow Up Note" button is now hidden on encounters that have no Encounter Payors — fewer half-completed notes.
  • If you're a hybrid supervisor (cover both ARR and ZB), you keep access to both — no special configuration needed.

⚙️ If you're a Salesforce Admin (Al / Naomi)

Substantial new metadata, but designed to layer cleanly on top of the existing org.

  • 4 new public groups for ARR client routing (Christus + NWM teams + supervisors).
  • 2 new sharing rules on Case (criteria-based, keyed on Record Type + Client + Status).
  • 3 new queues (ARR_Newly_Unassigned, ARR_Collections, ARR_Offshore_Adjustment_Review).
  • 4 new permission sets + 3 new permission set groups for ARR roles. Add a user to an ARR Permission Set Group and they're set up.
  • ~25 new custom fields on Case (Imported Payor data, ARR-specific commission fields, etc.) and several new Encounter Payor formula fields.
  • New Validation Rules enforce that ARR-only picklist values don't land on ZB encounters (and vice versa for Root Causes).
  • One Lightning page rebuild: ARR encounters use a dedicated Lightning Record Page (Titan_Health_ARR_Encounter_Record_Page) with sections tuned for ARR workflows.
  • All 25 ARR Encounter Guidance records are loaded — they drive automatic Next Owner routing when status codes change.

🔗 If you're working on Integrations (Tim / Kicksaw)

Two new automation hooks, plus the archival pipeline ready for activation.

  • Historic Encounter Archival pipeline (TH-345) is fully deployed: a REST endpoint exposes flagged encounters for Athena ingestion, then encounters are hard-deleted after a 7-day safety window.
  • Schedulables are deployed but inactive — turning them on in production is an explicit cutover step (decide cadence first).
  • Daily encounter staging continues to run at 14:50 UTC — it processes whatever has the "Imported - Pending Staging" status and resolves the Account from Facility Prefix.
  • Audit log lives on every Archive_Run__c record — what was attempted, what succeeded, what failed.
