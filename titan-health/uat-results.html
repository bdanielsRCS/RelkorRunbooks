TH-486 / TH-489 — R3 Sharing Model

What It Does

Release 3 adds Accounts Receivable Recovery (ARR) as a second Line of Business alongside Zero Balance (ZB). The sharing model enforces:

  • LOB Isolation — ZB users cannot see ARR encounters, and vice versa
  • Client Isolation — ARR users only see encounters for the clients they are assigned to (e.g., NWM collector sees only NWM encounters, not ABC)
  • Dual-LOB Support — A single user can work both ARR and ZB with correct isolation per LOB
  • Two-Tier ZB Access — Auditors get Read Only, Collectors get Read/Write

How It Works

Case OWD = Private (no one sees anything by default)
         │
         ├── ZB Access: Role-based groups (automatic via role assignment)
         │     ├── ZB_Encounter_Read_Only_Access → Reimbursement Auditors I-IV
         │     └── ZB_Encounter_Read_Edit_Access → Payor Collections Specs I-IV
         │
         └── ARR Access: Client-specific manual groups
               ├── ARR_Client_NWM → Users assigned to Northwestern Memorial
               ├── ARR_Client_ABC → Users assigned to Atlantic Blue Cross
               └── (one group per client, scalable to ~45 clients)

Sharing Rules (Criteria-Based):

  • ZB rules use RecordType = Zero Balance (ZB) + Status Code ≠ Unassigned
  • ARR rules use RecordType = Accounts Receivable Recovery (ARR) + Import Client = [code]

Key Design Decision: ARR sharing uses RecordTypeId (not the LOB__c field) to match the existing production ZB sharing rule pattern. This ensures sharing rules apply to all 5.3M production records correctly.

Known Item: ARR Users Can See ZB Encounters

Observation

In the UAT test results, Sarah Collins (ARR NWM Collector) sees 3.8M ZB records in addition to her 32 ARR records. James Wright (ZB Auditor) sees zero ARR records. The isolation is one-directional: ZB users can't see ARR, but ARR users CAN see ZB.

Why This Happens

The existing ZB sharing model (built before Release 3) uses role-based public groups:

ZB Group Members Access
ZB_Encounter_Read_Only_Access Reimbursement Auditor I-IV roles, CSM role Read
ZB_Encounter_Read_Edit_Access Payor Collections Specialist I-IV roles, Claims Analyst role Edit

ARR users share those same roles (e.g., Sarah Collins is a Payor Collections Specialist II). Because the ZB groups use roles (not individual users), anyone in those roles automatically gets ZB access — including ARR users.

ZB Group uses → Role: Payor_Collections_Specialist_II
                    ↑
              Sarah Collins has this role (she's an ARR user)
                    ↓
              Result: Sarah automatically gets ZB access through her role

The new ARR groups use manual membership (individual users, not roles). That's why the reverse doesn't happen — James Wright (ZB Auditor) is NOT manually added to any ARR group, so he sees zero ARR records.

Why ARR Can't Use Role-Based Groups Like ZB

ZB works with role-based groups because all ZB users see all ZB encounters — there's no client-level segmentation. Same role = same access = fine.

ARR requires client-level isolation: a NWM collector must not see ABC cases. But an NWM collector and an ABC collector can both be Payor_Collections_Specialist_II. If access is tied to the role, both see everything — no way to separate NWM from ABC within the same role. That's why ARR must use manual groups.

Decision Required: How Should Cross-LOB Access Work?

Option Description Impact
A. Accept the cross-over ARR users see ZB encounters automatically via their role. Users can work both LOBs without being explicitly added to ZB groups. No changes needed. Simplest. But no way to have an ARR-only user who can't see ZB.
B. Switch ZB to manual groups Change ZB groups from role-based to manual membership (matching the ARR pattern). Users only see ZB if explicitly added. Both LOBs work the same way. One-time migration: move all current ZB users from role membership to individual user membership. New ZB users must be manually added (no longer automatic via role).
C. Create ARR-specific roles Separate the role hierarchy so ARR users are in different roles than ZB users. ZB role-based groups would no longer include ARR users. Requires new roles — client previously stated they don't want new roles.

Recommendation

If the expectation is that ARR-only users should not see ZB encounters, Option B is the best path. It creates a consistent model across both LOBs (manual groups for everyone), requires no new roles, and Al's team already manages manual group membership for ARR. The one-time migration of existing ZB users to manual membership can be scripted.

If it's acceptable that all users see ZB by default (since everyone shares the same roles), Option A requires no changes.

Key question for the client: "Is it a problem that ARR users can also see ZB encounters, or is that expected since they share the same roles?"

Adding a New ARR Client (Ongoing Admin Process)

When Titan Health onboards a new ARR client:

  1. Create Public Group: Setup → Public Groups → New — ARR - Client [CODE]
  2. Create Sharing Rule: Setup → Sharing Settings → Case → New Rule — RecordType = ARR AND Import Client = [CODE] → Share with group at Read/Write
  3. Add Users: Add assigned collectors and supervisors to the new group

No code, no deployment. Access takes effect after sharing rule recalculation.

Scalability: Salesforce limits criteria-based sharing rules to 50 per object. Each ARR client = 1 rule. Supports ~45 clients. Apex Managed Sharing solution is built and tested if needed beyond that limit.

TH-345 — Historic Archival Process

What It Does

When an Encounter (Case) has been closed for 24 months, the archival pipeline:

  1. Identifies eligible encounters — formula field Archival_Eligible__c returns TRUE when ClosedDate > 730 days + status is Closed or Confirmed No Opportunity
  2. Archives to cold storage (Athena) — batch job collects the encounter + all child records, writes via integration, stamps Archival_Status__c = 'Archive Completed'
  3. Waits 7 days — buffer window for spot-checking before permanent deletion
  4. Hard-deletes from Salesforce — separate batch job removes archived encounters + cascading children, empties recycle bin
Eligibility Check → Archive Batch → Verify & Audit → 7-Day Buffer → Delete Batch
(formula field)     (collects all     (Archive_Run__c    (spot-check     (hard delete +
                     children,         audit record)      window)         emptyRecycleBin)
                     writes to
                     Athena)

Architecture

Pull-model integration (post-pivot, 2026-04-16): The batch job only flags eligible encounters with Archival_Status__c = 'Archiving In Progress'. Tim's external integration calls GET /services/apexrest/archival/encounters (implemented by ArchivalDataService), pulls encounters + all children + grandchildren as JSON, writes to Athena, then stamps Archive Completed + Archive_Completed_Date__c back on the Case. The SOQL queries the REST service runs are stored in Archival_Config__mdt records so they can be tuned without a deploy. The earlier IArchiveWriter / ArchivePayload / MockArchiveWriter abstraction was removed.

Archival Scope (per encounter):

  • Encounter (Case) — 112+ custom fields
  • Encounter Payor (Master-Detail → Case)
  • Financial Activity (Master-Detail → Encounter Payor)
  • Encounter Code Change (Master-Detail → Case)
  • Document Request (Master-Detail → Case)
  • Task, Event, EmailMessage, CaseComment (standard children)
  • ContentDocumentLink (files)
