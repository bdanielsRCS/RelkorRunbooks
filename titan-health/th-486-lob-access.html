Task Description & Reference Documentation

Current State

  • Case OWD is set to Private
  • ZB sharing model is fully operational using role-based public groups:
    • ZB - Encounter Read Only Access (Reimbursement Auditors I–IV, Client Success Manager)
    • ZB - Encounter Read/Edit Access (Payor Collections Specialists I–IV, Claims Analyst)
  • ZB sharing rules are active — all ZB users see all ZB encounters (no client-level isolation)
  • ARR line of business has no sharing model — ARR users currently cannot see any ARR encounters due to Private OWD
  • ZB and ARR record types both exist on Case
  • Role hierarchy is production-current (Program Administrator > Supervisor > worker roles)

Ideal State

  • ARR users can see and work encounters for only the clients they are assigned to (client-level data isolation)
  • Program Admins can control LOB access by adding/removing users from client-specific public groups — no code changes required
  • ARR and ZB users are fully isolated from each other's encounters unless a user is intentionally assigned to both
  • Dual-LOB users (working both ARR and ZB) see the correct encounters for each LOB
  • Field-level security enforces tiered access: collectors vs. supervisors vs. admins
  • New ARR clients can be onboarded through a simple group + sharing rule process

Technical Configuration Notes

Prerequisites

1. Public Groups

Create 4 manual-membership public groups. Grant Access Using Hierarchies checked on all.

Label API Name Purpose
ARR - All Users ARR_All_Users UI visibility only (list views, reports). NOT used for data access
ARR - Supervisors ARR_Supervisors Queue membership for ARR queues (see TH-489)
ARR - Client NWM ARR_Client_NWM Data sharing — Northwestern Memorial cases
ARR - Client ABC ARR_Client_ABC Data sharing — Atlantic Blue Cross cases

Key difference from ZB: ARR groups use manual membership (individual users), not roles. The same role (e.g., Payor Collections Specialist II) could work any ARR client, so role-based groups would not provide client isolation.

Do NOT add members yet — that happens after sharing rules are in place (step 3 below).

2. Sharing Rules (Client-Specific)

Create one criteria-based sharing rule per ARR client:

Rule Name Criteria Share With Access
ARR_Client_NWM_Access LOB__c = ARR AND Import_Client__c = NWM ARR - Client NWM Read/Write
ARR_Client_ABC_Access LOB__c = ARR AND Import_Client__c = ABC ARR - Client ABC Read/Write

⚠️ Do NOT create a blanket ARR LOB-wide sharing rule. A rule like "LOB = ARR → ARR All Users" would let every ARR user see every client's cases, defeating client isolation entirely.

Allow time for sharing rule recalculation (4M+ records).

3. Permission Sets

Three tiered permission sets:

ARR Collector Base (ARR_Collector_Base)

  • Case: Read, Edit (no Create, no Delete)
  • ARR Record Type: Visible
  • Read + Edit: LOB, Import Client, Import Client Identifier, Next Work Date, Result Code, Root Cause, Payor
  • Read Only: Status Code Category, Contingency Rate, Encounter Amount, ARR Collector, ARR Supervisor

ARR Supervisor Elevated (ARR_Supervisor_Elevated)

  • Case: Create, Read, Edit (no Delete)
  • ARR Record Type: Visible
  • Read + Edit: All ARR fields (including Status Code Category, Contingency Rate, Encounter Amount, ARR Collector, ARR Supervisor)

ARR Admin (ARR_Admin)

  • Case: Create, Read, Edit (no Delete)
  • Payor__c: Create, Read, Edit (no Delete)
  • ARR Record Type: Visible
  • Read + Edit: All ARR fields

4. Record Type Picklist Filtering

Restrict Root Cause picklist values by record type:

  • ARR available values: Billing Error, Insurance Denial, Patient Responsibility, Other
  • ARR must NOT include: Coding Error (ZB-specific)
  • ZB: No change — all values including Coding Error

5. User Assignments

User Type Public Groups Permission Set
ARR Collector (single client) ARR_Client_[CODE], ARR_All_Users ARR Collector Base
ARR Collector (multi-client) ARR_Client_[CODE1], [CODE2], ARR_All_Users ARR Collector Base
ARR Supervisor ARR_Client_[CODEs], ARR_Supervisors, ARR_All_Users ARR Supervisor Elevated
ZB-only user (none needed) ZB Collector Base
Admin ARR_Client_[all], ARR_Supervisors, ARR_All_Users ARR Admin

ZB access remains automatic via role-based groups — no additional assignment needed.

6. List Views

Create ARR-specific list views shared only with ARR groups:

List View Filter Shared With
ARR - My Encounters LOB = ARR AND Owner = Current User ARR - All Users
ARR - Unassigned Queue LOB = ARR AND Owner = Queue: ARR - Unassigned ARR - Supervisors
ARR - Collections Queue LOB = ARR AND Owner = Queue: ARR - Collections ARR - Supervisors

Suggested columns: Case Number, Subject, Import Client, Status, Encounter Amount, Next Work Date

7. Payor Validation Rule

Create validation rule Payor_Must_Match_Client_And_LOB on Case:

  • Condition: Payor is selected AND (Payor's Client__c ≠ Case's Import_Client__c OR Payor's LOB__c ≠ Case's LOB__c and Payor's LOB__c ≠ "Both")
  • Error: "Selected Payor does not match this Encounter's Client and Line of Business."
  • Location: Payor field

A lookup filter would be better UX but cannot reference text fields. Validation rule provides equivalent server-side enforcement.

Adding a New ARR Client (Runbook)

  1. Create Public Group: ARR - Client [CODE] — manual membership, Grant Access Using Hierarchies checked
  2. Create Sharing Rule: Criteria = LOB = ARR AND Import Client = [CODE] → Share with ARR - Client [CODE] at Read/Write
  3. Add Users: Assign collectors and supervisors to the new group

No code, no deployment. Access takes effect after sharing rule recalculation.

Scalability: SF limits criteria-based sharing rules to 50 per object. Each ARR client = 1 rule. Supports ~45 clients accounting for ZB rules. Apex Managed Sharing solution is built and tested if needed.
