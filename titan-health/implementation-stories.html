Titan Health — Release 3: ARR Sharing Model Implementation Stories

Author: Bryant Daniels Date: 2026-04-02 For: Al Reveles (Titan Health) Reference: SA-SOLUTION-SHARING-MODEL (docs/)

Prerequisites

These stories assume the following are already in place (confirmed in production):

  • Case OWD = Private
  • ZB record type and ARR record type both exist on Case
  • Role hierarchy is production-current (Program Administrator > Supervisor > worker roles)
  • ZB groups already created:
    • ZB - Encounter Read Only Access (Reimbursement Auditors I–IV, Client Success Manager)
    • ZB - Encounter Read/Edit Access (Payor Collections Specialists I–IV, Claims Analyst)
  • ZB sharing rules already active

Story 1: Create ARR Client-Specific Public Groups

As a Salesforce Admin, I want to create Public Groups for each ARR client, So that I can control which users see which client's ARR encounters.

Why

ARR requires client-level data isolation. Unlike ZB (where all users see all ZB cases), ARR users should only see encounters for clients they are assigned to. Each client gets its own Public Group, and sharing rules grant access based on group membership.

Steps to Implement

  1. Go to Setup > Users > Public Groups
  2. Create the following groups:
Label Group Name (API) Description Grant Access Using Hierarchies
ARR - All Users ARR_All_Users UI visibility — list views and reports for ARR users. NOT used for data access. Checked
ARR - Supervisors ARR_Supervisors Queue membership for ARR unassigned/collections queues Checked
ARR - Client NWM ARR_Client_NWM Data sharing — controls who sees Northwestern Memorial cases Checked
ARR - Client ABC ARR_Client_ABC Data sharing — controls who sees Atlantic Blue Cross cases Checked

  1. For each group, set the Type to the following:

    • All groups above are manual membership (add individual users, NOT roles)
    • This is different from the ZB groups which are role-based. ARR groups must be manual because the same role (e.g., Payor Collections Specialist II) could work any ARR client.

  2. Do NOT add members yet — that happens in Story 6 after sharing rules are in place.

Acceptance Criteria

Testing Steps

  1. Navigate to Setup > Public Groups
  2. Verify each group exists with the correct API name
  3. Click into each group and confirm "Grant Access Using Hierarchies" is checked
  4. Confirm member list is empty

Story 2: Create ARR Queues

As a Salesforce Admin, I want to create queues for ARR encounters, So that imported ARR encounters land in an unassigned queue that only supervisors can see.

Why

When ARR encounters are imported, they should not be visible to collectors until a supervisor assigns them. Queue-owned records inherit the OWD (Private), so only queue members can see them.

Steps to Implement

  1. Go to Setup > Queues (search "Queues" in Quick Find)
  2. Create the following queues:
Queue Label Queue Name Supported Objects Queue Members
ARR - Unassigned ARR_Unassigned Case ARR - Supervisors group
ARR - Collections ARR_Collections Case ARR - Supervisors group
  1. For each queue:
    • Add the ARR - Supervisors public group as a member
    • Do NOT add individual collectors
    • Uncheck "Send Email to Members" (optional — depends on notification preferences)

Acceptance Criteria

Testing Steps

  1. Navigate to Setup > Queues
  2. Verify both queues exist with correct names
  3. Click into each queue and confirm ARR - Supervisors is the only member
  4. Verify Case is listed under Supported Objects

Story 3: Create ARR Sharing Rules (Client-Specific)

As a Salesforce Admin, I want to create criteria-based sharing rules that grant access to ARR encounters by client, So that users in a client's group can see and edit that client's cases.

Why

With OWD Private, no one sees any Cases by default. These rules open access for each client's group to only that client's ARR encounters. This is the core mechanism for client-level data isolation.

Steps to Implement

  1. Go to Setup > Sharing Settings
  2. Scroll down to Case Sharing Rules
  3. Click New and create the following rules:

Rule 1: ARR Client NWM Access | Field | Value | |---|---| | Label | ARR Client NWM Access | | Rule Name | ARR_Client_NWM_Access | | Rule Type | Based on criteria | | Criteria | Line of Business (LOB__c) equals ARR AND Import Client (Import_Client__c) equals NWM | | Share with | Public Group: ARR - Client NWM | | Access Level | Read/Write |

Rule 2: ARR Client ABC Access | Field | Value | |---|---| | Label | ARR Client ABC Access | | Rule Name | ARR_Client_ABC_Access | | Rule Type | Based on criteria | | Criteria | Line of Business (LOB__c) equals ARR AND Import Client (Import_Client__c) equals ABC | | Share with | Public Group: ARR - Client ABC | | Access Level | Read/Write |

  1. Wait for sharing rule recalculation to complete (this may take time with 4M+ records)

IMPORTANT: Do NOT Create a Blanket ARR LOB Rule

Unlike ZB (which has LOB-wide Read rules), ARR does NOT get a blanket LOB-wide rule. If you created a rule like "LOB = ARR → ARR All Users", it would let every ARR user see every client's cases, defeating client isolation.

Acceptance Criteria

Testing Steps

  1. Navigate to Setup > Sharing Settings > Case Sharing Rules
  2. Verify both rules appear in the list
  3. Click into each rule and confirm criteria and target group are correct
  4. Confirm no rule exists that shares ALL ARR cases to a single group

Story 4: Create ARR Permission Sets

As a Salesforce Admin, I want to create permission sets that control what ARR users can do with encounter records, So that collectors, supervisors, and admins have the right field-level access.

Why

Sharing rules control which records you see. Permission sets control what you can do with those records (which fields you can read/edit, whether you can create records, etc.).

Steps to Implement

Create the following permission sets under Setup > Permission Sets > New:

Permission Set 1: ARR Collector Base | Setting | Value | |---|---| | Label | ARR Collector Base | | API Name | ARR_Collector_Base | | License | Salesforce | | Object: Case | Read, Edit (no Create, no Delete) | | Record Type: ARR | Visible | | Field Access — Read + Edit | LOB, Import Client, Import Client Identifier, Next Work Date, Result Code, Root Cause, Payor | | Field Access — Read Only | Status Code Category, Contingency Rate, Encounter Amount, ARR Collector, ARR Supervisor |

Permission Set 2: ARR Supervisor Elevated | Setting | Value | |---|---| | Label | ARR Supervisor Elevated | | API Name | ARR_Supervisor_Elevated | | License | Salesforce | | Object: Case | Create, Read, Edit (no Delete) | | Record Type: ARR | Visible | | Field Access — Read + Edit | All ARR fields including Status Code Category, Contingency Rate, Encounter Amount, ARR Collector, ARR Supervisor |

Permission Set 3: ARR Admin | Setting | Value | |---|---| | Label | ARR Admin | | API Name | ARR_Admin | | License | Salesforce | | Object: Case | Create, Read, Edit (no Delete) | | Object: Payor__c | Create, Read, Edit (no Delete) | | Record Type: ARR | Visible | | Field Access — Read + Edit | All ARR fields |

Acceptance Criteria

Testing Steps

  1. Navigate to Setup > Permission Sets
  2. Verify all three exist
  3. Click into ARR Collector Base > Object Settings > Case
  4. Confirm Read/Edit on Case, no Create
  5. Confirm field access: Status_Code_Category__c, Contingency_Rate__c, Encounter_Amount__c are Read Only
  6. Click into ARR Supervisor Elevated and verify all fields are Read + Edit

Story 5: Configure Record Type Picklist Filtering

As a Salesforce Admin, I want to restrict picklist values by record type, So that ARR users only see Root Cause values applicable to ARR, and ZB users see values applicable to ZB.

Why

Different LOBs have different valid Root Cause values. "Coding Error" is a ZB-specific root cause that should not appear on ARR encounters.

Steps to Implement

  1. Go to Setup > Object Manager > Case > Record Types

  2. Click on the ARR record type

  3. Click the Root Cause picklist

  4. Click Edit

  5. Ensure the following values are available for ARR:

    • Billing Error
    • Insurance Denial
    • Patient Responsibility
    • Other

  6. Ensure Coding Error is NOT available for ARR (move it to the "Available Values" column, not "Selected Values")

  7. Click Save

  8. Click on the ZB record type

  9. Click the Root Cause picklist

  10. Verify all values are available for ZB (including Coding Error)

Acceptance Criteria

Testing Steps

  1. Log in as an ARR user (or use the ARR record type)
  2. Create or edit a Case with the ARR record type
  3. Click the Root Cause dropdown
  4. Verify "Coding Error" does NOT appear
  5. Switch to ZB record type and verify "Coding Error" DOES appear

Story 6: Assign Users to Groups and Permission Sets

As a Salesforce Admin, I want to assign users to the correct Public Groups and Permission Sets, So that each user sees the right encounters and has the right level of access.

Why

This is where the sharing model comes to life. Group membership determines what a user can see. Permission set assignment determines what they can do.

Steps to Implement

For each ARR Collector:

  1. Go to Setup > Public Groups > ARR - Client [CODE] (e.g., ARR - Client NWM)
  2. Click Edit
  3. Add the user under Group Members (search for their name, select "Users" type)
  4. Also add them to ARR - All Users (for list view visibility)
  5. Go to the user's record > Permission Set Assignments
  6. Assign ARR Collector Base

For each ARR Supervisor:

  1. Add to ARR - Client [CODE] for each client they manage
  2. Add to ARR - Supervisors (for queue visibility)
  3. Add to ARR - All Users
  4. Assign ARR Supervisor Elevated permission set

For ZB users: No action needed — ZB groups are role-based and membership is automatic. Users in Reimbursement Auditor I–IV and Client Success Manager roles automatically get ZB Read Only access. Users in Payor Collections Specialist I–IV and Claims Analyst roles automatically get ZB Read/Write access.

For Dual-LOB users (work both ARR and ZB):

  1. Add to the appropriate ARR - Client [CODE] group(s)
  2. Add to ARR - All Users
  3. Assign ARR Collector Base (or ARR Supervisor Elevated if they supervise ARR)
  4. ZB access is automatic via their role — no additional ZB group assignment needed

Quick Reference: What Goes Where

User Type Public Groups Permission Set ZB Access
ARR Collector (single client) ARR_Client_[CODE], ARR_All_Users ARR Collector Base Automatic via role
ARR Collector (multi-client) ARR_Client_[CODE1], ARR_Client_[CODE2], ARR_All_Users ARR Collector Base Automatic via role
ARR Supervisor ARR_Client_[CODE(s)], ARR_Supervisors, ARR_All_Users ARR Supervisor Elevated Automatic via role hierarchy
ZB-only user (none needed) ZB Collector Base Automatic via role
Admin ARR_Client_[all], ARR_Supervisors, ARR_All_Users ARR Admin Automatic via role hierarchy

Acceptance Criteria

Testing Steps

  1. Navigate to Setup > Public Groups > ARR - Client NWM
  2. Click "View All Users" and verify the expected users appear
  3. Navigate to a user's detail page and verify their permission set assignments
  4. Repeat for each client group

Story 7: Create ARR List Views (Scoped by LOB)

As a Salesforce Admin, I want to create ARR-specific list views shared only with ARR users, So that ZB users don't see ARR list views in their dropdown, and ARR users have relevant views.

Why

List views should be scoped by LOB. ZB users shouldn't see ARR views cluttering their UI, and vice versa.

Steps to Implement

  1. Go to the Cases tab
  2. Create the following list views:

List View 1: ARR - My Encounters | Setting | Value | |---|---| | Name | ARR - My Encounters | | Filter | LOB equals ARR AND Case Owner equals current user | | Shared with | Public Group: ARR - All Users | | Columns | Case Number, Subject, Import Client, Status, Encounter Amount, Next Work Date |

List View 2: ARR - Unassigned Queue | Setting | Value | |---|---| | Name | ARR - Unassigned Queue | | Filter | LOB equals ARR AND Case Owner equals Queue: ARR - Unassigned | | Shared with | Public Group: ARR - Supervisors | | Columns | Case Number, Subject, Import Client, Encounter Amount, Created Date |

List View 3: ARR - Collections Queue | Setting | Value | |---|---| | Name | ARR - Collections Queue | | Filter | LOB equals ARR AND Case Owner equals Queue: ARR - Collections | | Shared with | Public Group: ARR - Supervisors | | Columns | Case Number, Subject, Import Client, Encounter Amount, Status |

  1. For each list view, use the Sharing Settings option to share with the specified group only (not "All Users")

Acceptance Criteria

Testing Steps

  1. Log in as an ARR user
  2. Navigate to Cases tab
  3. Verify ARR list views appear in the dropdown
  4. Log in as a ZB-only user
  5. Navigate to Cases tab
  6. Verify ARR list views do NOT appear

Story 8: Configure Payor Validation Rule

As a Salesforce Admin, I want to ensure that when a user selects a Payor on an Encounter, the Payor matches the Encounter's Client and LOB, So that users can't accidentally associate the wrong payor with an encounter.

Why

Each Payor is associated with a Client and LOB. If a user is working a Northwestern Memorial ARR encounter, they should only be able to select Payors that belong to Northwestern Memorial and the ARR line of business.

Steps to Implement

  1. Verify the Payor__c custom object has these fields:

    • Name__c (Payor name)
    • Payor_Code__c (Code)
    • LOB__c (Picklist: ARR | ZB | Both)
    • Client__c (Text — matches Case.Import_Client__c)

  2. Go to Setup > Object Manager > Case > Validation Rules

  3. Create (or verify existing) validation rule:

Field Value
Rule Name Payor_Must_Match_Client_And_LOB
Active True
Error Condition Payor is selected AND (Payor's Client does not match Case's Import Client OR Payor's LOB does not match Case's LOB and Payor's LOB is not "Both")
Error Message "Selected Payor does not match this Encounter's Client and Line of Business. Please select a Payor that matches."
Error Location Payor field

Note on Lookup Filters

A lookup filter would provide a better UX (filtering the Payor picker in real-time), but lookup filters cannot reference text fields. Since both Import_Client__c (Case) and Client__c (Payor) are text fields, a lookup filter is not feasible. The validation rule provides equivalent server-side enforcement.

Acceptance Criteria

Testing Steps

  1. Open an ARR NWM encounter
  2. Try to select a Payor that belongs to ABC → should fail validation
  3. Try to select a Payor that belongs to NWM with LOB = ARR → should save
  4. Try to select a Payor with LOB = "Both" and Client = NWM → should save
  5. Open a ZB encounter and try to select an ARR-only Payor → should fail

Critical Checks

Adding a New ARR Client (Ongoing Process)

When Titan Health onboards a new ARR client, the admin workflow is:

  1. Create Public Group: Setup > Public Groups > New

    • Label: ARR - Client [CODE]
    • Group Name: ARR_Client_[CODE]
    • Grant Access Using Hierarchies: Checked
    • Members: Users assigned to that client

  2. Create Sharing Rule: Setup > Sharing Settings > Case > New Rule

    • Criteria: LOB = ARR AND Import Client = [CODE]
    • Share with: ARR - Client [CODE]
    • Access Level: Read/Write

  3. Add Users: Add assigned collectors and supervisors to the new group

That's it — no code, no deployment, no record-level changes. Access takes effect after sharing rule recalculation completes.

Scalability Note

Salesforce limits criteria-based sharing rules to 50 per object. Each ARR client requires one rule. At the current pace, this supports ~45 clients (accounting for ZB rules). If Titan Health expects to exceed that limit, an Apex Managed Sharing solution has been built and tested — flag for activation when planning client onboarding.
