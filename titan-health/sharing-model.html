Titan Health — Release 3 Sharing Model Solution

Prepared by: Relkor Cloud Solutions LLC Date: 2026-04-01 Status: Draft — For SA Review Scratch Org: titan-r3-poc (expires 2026-04-28)

1. Business Problem

Titan Health operates two Lines of Business (LOBs) on a single Salesforce org:

  • Zero Balance (ZB) — existing, live in production
  • Accounts Receivable Recovery (ARR) — new, being added in Release 3

Both LOBs use the Case object to represent Encounters. The org currently has a Private OWD on Case with criteria-based sharing rules that open access for ZB users.

Release 3 introduces ARR with a critical new constraint: client-level data isolation. ARR Encounters are segmented by hospital client (e.g., Northwestern Memorial, Atlantic Blue Cross). Users should only see Encounters for the clients they are assigned to.

3. Options Evaluated

Option A: Role Hierarchy Segmentation

Create ARR-specific roles per client (e.g., ARR_Collector_NWM, ARR_Collector_ABC). Role hierarchy naturally controls visibility.

Pros Cons
Clean, well-understood model Users can only have ONE role — kills multi-client assignment
Built-in upward visibility Requires new roles (stakeholder said no)
No Apex needed Doesn't support users spanning LOBs

Verdict: Not viable. John explicitly stated users can work multiple clients and both LOBs. A user can only hold one role.

Option B: Restriction Rules

Use Restriction Rules to hide records even when broader sharing rules grant access. E.g., "If user LOB != record LOB, restrict."

Pros Cons
Clean subtraction from existing access Only supports simple field-level criteria
No code Can't do client-level matching (no "User.Client IN Record.Client" logic)
Works alongside sharing rules Limited to specific editions

Verdict: Partially viable. Could handle LOB isolation (hide ZB from ARR users), but cannot solve client-level isolation — there's no way to match a user's assigned clients against the record's client field in a Restriction Rule. Would need to be combined with another approach.

Option C: Case Teams

Use Case Teams to manage per-record access dynamically.

Pros Cons
Per-record granularity Not scalable for 4.2M records — team membership is per-case, not per-group
Built-in No bulk assignment mechanism
Al confirmed they only use teams as a "catcher" for audit trail

Verdict: Not viable at this volume. Case Teams are per-record; managing team membership across millions of records for client assignment is not practical.

Option D: Criteria-Based Sharing Rules + Public Groups (Fully Declarative)

Create client-specific Public Groups and matching criteria-based sharing rules. Admins manage client assignment by adding/removing users from groups.

Pros Cons
Fully declarative — no code to maintain Salesforce limits: 50 criteria-based sharing rules per object
Delegated admins already manage groups ~1 rule per client for ARR (+ existing ZB rules)
Matches existing ZB pattern Won't scale past ~20–25 ARR clients
Auditable, visible in Setup Adding a new client requires creating a group + sharing rule

Verdict: Best fit for current scope. Titan Health currently has a small number of ARR clients. This approach is fully maintainable by the existing team without Apex skills. If client count grows past 20–25, upgrade to Option E.

Option E: Apex Managed Sharing (Programmatic)

Use Apex triggers to create CaseShare records dynamically based on the Case's Import_Client__c field and the user's Public Group membership.

Pros Cons
Unlimited scalability (no 50-rule limit) Requires Apex code — no one on team to maintain
Dynamic — handles new clients without new rules Harder to debug and audit
Trigger-based, automatic Requires batch job for bulk recalculation
Already built and tested in scratch org More complex failure modes

Verdict: Strong fallback. The code exists in the scratch org and has been tested. Not recommended as primary approach given team constraints, but should be kept as an upgrade path.

Option F: Hybrid — Declarative Primary + Apex Fallback (Recommended by scratch org)

Use criteria-based sharing rules for current clients, with the Apex sharing framework ready to activate if client count exceeds limits.

Verdict: This was the direction in the scratch org, but the implementation had issues (see Section 4).

4. Recommended Solution

Option D: Criteria-Based Sharing Rules + Client-Specific Public Groups

Pure declarative. No Apex in the primary path. The Apex code remains in the codebase as a documented upgrade path but is not active.

Why Not Hybrid?

The scratch org implementation mixed both approaches, but this introduces complexity without benefit at current scale. If you have 5 clients, you need 5 sharing rules — well within the 50-rule limit. Adding Apex sharing on top creates two access paths to audit, two mechanisms to debug, and a code dependency for a team that can't maintain Apex.

Keep it simple. Go fully declarative now. The Apex code is there if you need it later.

4.2 The Three Layers

Layer 1 — OWD Private (Foundation)

Already in place. No changes needed. Every Case is invisible by default.

Layer 2 — LOB Isolation

LOB Mechanism Who Gets Access
ZB Two criteria-based sharing rules by access level:
LOB__c = 'ZB' → ZB_Encounter_Read_Only_Access (Read) Reimbursement Auditors I–IV, Client Success Manager (role-based)
LOB__c = 'ZB' → ZB_Encounter_Read_Edit_Access (Read/Write) Payor Collections Specialists I–IV, Claims Analyst (role-based)
ARR No LOB-wide rule. Access comes exclusively through client-specific rules (Layer 3) Only users assigned to specific clients

This is the critical difference from ZB. ZB uses a two-tier role-based model — certain roles get Read Only, others get Read/Write, and Supervisors/Program Administrators inherit access via "Grant Access Using Hierarchies." For ARR, there is no blanket LOB access — you only see the clients you're assigned to. Cross-LOB isolation is achieved by the absence of any sharing rule that would grant access across LOBs.

Layer 3 — Client-Level Access (ARR Only)

One criteria-based sharing rule per ARR client:

Rule Name Criteria Shared With Access Level
ARR_Client_NWM_Access LOB__c = 'ARR' AND Import_Client__c = 'NWM' ARR_Client_NWM Read/Write
ARR_Client_ABC_Access LOB__c = 'ARR' AND Import_Client__c = 'ABC' ARR_Client_ABC Read/Write
(one per client)

Who goes in each client group:

  • Collectors assigned to that client
  • Supervisors assigned to that client
  • Directors/VPs who oversee that client

Layer 4 — Queue Visibility

Queue Members Effect
ARR_Unassigned Supervisors, Admins Only queue members see queue-owned (unassigned) cases
ARR_Collections Supervisors, Admins Same pattern for collections workflow
ZB_Unassigned ZB Supervisors, Admins Existing, unchanged

Collectors are explicitly not queue members. They cannot see unassigned encounters until a supervisor assigns one to them.

4.3 Public Groups

ZB Groups (Existing — Created by Al Reveles, 2/17/2026)

Group API Name Type Purpose Members
ZB - Encounter Read Only Access ZB_Encounter_Read_Only_Access Role-based ZB data sharing — Read Only Reimbursement Auditor I–IV, Client Success Manager
ZB - Encounter Read/Edit Access ZB_Encounter_Read_Edit_Access Role-based ZB data sharing — Read/Write Payor Collections Specialist I–IV, Claims Analyst

Both ZB groups have Grant Access Using Hierarchies = true, so Supervisors and Program Administrators inherit access automatically through the role hierarchy.

ARR Groups (New — To Be Created)

Group Type Purpose Members
ARR_All_Users Manual List view sharing, reporting (NOT data sharing) All users who work ARR — manually maintained
ARR_Supervisors Manual Queue membership, supervisor-level features Supervisors who manage ARR — manually maintained
ARR_Client_NWM Manual Data sharing — controls who sees NWM cases Users assigned to NWM (collectors + supervisors)
ARR_Client_ABC Manual Data sharing — controls who sees ABC cases Users assigned to ABC (collectors + supervisors)
(one per ARR client) Manual Data sharing Users assigned to that client

Why ZB groups are role-based but ARR client groups are manual:

  • ZB is client-agnostic — access is determined by job function. Reimbursement Auditors always audit ZB encounters (Read Only). Payor Collections Specialists and Claims Analysts always work ZB encounters (Read/Write). Role-based groups work because the role determines the access level.
  • ARR requires client-level isolation — a Payor Collections Specialist assigned to NWM should not automatically see ABC cases. Since the same role can be assigned to different clients, role-based groups cannot provide client-level isolation. Manual groups are required.
  • ARR_All_Users and ARR_Supervisors are manual because any role could potentially work ARR. These are for UI visibility and queue membership, not data sharing.

Important distinction:

  • ARR_All_Users is for UI visibility (list views, reports) — NOT for data sharing rules
  • ARR_Client_* groups are for data sharing — these control which cases users can see
  • A user in ARR_Client_NWM but not ARR_Client_ABC can see NWM cases but not ABC cases

4.4 Role Hierarchy (Production — Unchanged)

Titan Health Management Solutions
└── Program Administrator
    ├── Client Success Manager
    └── Supervisor
        ├── Claims Analyst
        ├── Payor Collections Specialist I
        ├── Payor Collections Specialist II
        ├── Payor Collections Specialist III
        ├── Payor Collections Specialist IV
        ├── Reimbursement Auditor I
        ├── Reimbursement Auditor II
        ├── Reimbursement Auditor III
        └── Reimbursement Auditor IV

Key characteristics:

  • Roles are organized by job function and seniority tier
  • All worker roles (Claims Analyst, Payor Collections Specialists, Reimbursement Auditors) are peers under Supervisor
  • Tiers I–IV represent seniority levels, not access levels — all tiers within a function get the same Salesforce permissions
  • Roles map to ZB access levels: Reimbursement Auditors + Client Success Manager → ZB Read Only; Payor Collections Specialists + Claims Analyst → ZB Read/Write. This is why ZB groups are role-based.
  • Roles do NOT map to ARR client assignment — a Payor Collections Specialist could work any ARR client. ARR client-level access is determined by manual Public Group membership.
  • The Supervisor role inherits visibility from all subordinate roles via "Grant Access Using Hierarchies," giving Supervisors and Program Administrators full ZB access automatically
  • Actual ARR data access is controlled by OWD Private + criteria-based sharing rules, not by role hierarchy rollup

4.5 How User Assignment Works

Assigning a user to an ARR client (admin action):

  1. Add user to the client's Public Group (e.g., ARR_Client_NWM)
  2. Sharing rule automatically grants Read/Write to that client's cases
  3. No code, no deployment, no record-level changes

Removing a user from a client:

  1. Remove user from the client's Public Group
  2. Access is automatically revoked by the sharing engine

Adding a new ARR client:

  1. Create a new Public Group (ARR_Client_NEWCLIENT)
  2. Create a new criteria-based sharing rule: LOB=ARR AND Import_Client=NEWCLIENT → ARR_Client_NEWCLIENT (Read/Write)
  3. Add users to the group

This is admin-level work — no development needed.

6. Issue in Current Scratch Org

The POC scratch org has a rule that needs to be removed before production:

ARR_LOB_Access — grants Read to ALL ARR cases for ARR_All_Users

This breaks client isolation. An NWM collector can read ABC cases. The intent was to mirror ZB's LOB-wide read, but ARR's client isolation requirement means no blanket LOB access. Access must flow exclusively through client-specific groups.

Also reconsider: ARR_Supervisor_Full_Access — grants Edit to ALL ARR cases for ARR_Supervisors. Al's statement that supervisors default to one client and get added to others suggests supervisors should also be client-restricted. Replace this with adding supervisors to client-specific groups.

7. Scalability Path

Current state: ~2–5 ARR clients = 2–5 sharing rules. Well within the 50-rule limit.

Scaling plan:

Client Count Approach
1–20 Criteria-based sharing rules (fully declarative)
20–40 Monitor rule count, plan migration if needed
40+ Activate Apex Managed Sharing (code exists in scratch org, tested)

The Apex framework (ARRClientSharingService, CaseARRSharingTriggerHandler, ARRClientSharingBatch) is already built and tested. To activate:

  1. Deploy the Apex classes and trigger
  2. Remove criteria-based client rules (Apex replaces them)
  3. Run ARRClientSharingBatch to backfill CaseShare records

This is a future consideration, not a Release 3 concern.
