TH-345 — Historic Archival Process: Solution Design

Story: TH-345 [FF] Historic Archival Process Author: Bryant Daniels (SA), consolidating original notes by Mitch Date: 2026-04-06 Status: Draft — Pending ENG integration spec + client scope decisions Related: TH-221 (Data Archival Process)

1. Business Requirement

When an Encounter has been closed for 24 months, it should be archived to cold storage (Athena) and then hard-deleted from Salesforce.

Closed means the Encounter has a Status of:

  • Closed, OR
  • Confirmed No Opportunity

Both statuses set the ClosedDate field. The ClosedDate is the single trigger — the 24-month timer starts when ClosedDate is populated, regardless of which closed status was applied.

If an Encounter is reopened (status changed back from a closed status), the ClosedDate must reset, restarting the timer when it's eventually re-closed.

Data must only be hard-deleted from Salesforce after the archive write to Athena has been verified.

3. Component 1: Salesforce Metadata

3.1 Archival Status Picklist (Case)

Field: Archival_Status__c Type: Picklist Object: Case Values:

  • Archiving In Progress — Set when the batch job begins processing this record
  • Archive Completed — Set after successful write + verification to Athena
  • Archive Failed — Set if any step fails; record is re-eligible on next run Default: Blank (null) Notes: Must be visible on Encounter layouts and reportable. FLS should allow the batch job's running user to write this field.

3.2 Archival Trigger Formula (Case)

Field: Archival_Eligible__c Type: Formula (Checkbox) Object: Case

AND(
  NOT(ISBLANK(ClosedDate)),
  ClosedDate <= TODAY() - 730,
  OR(
    ISPICKVAL(Status_Code__c, "Closed"),
    ISPICKVAL(Status_Code__c, "Confirmed No Opportunity")
  ),
  ISBLANK(TEXT(Archival_Status__c))
)

Logic:

  • ClosedDate is populated AND older than 730 days (24 months)
  • Status is in a closed state (belt-and-suspenders with the date check)
  • Archival Status is blank (never attempted before, or was reset after failure)

3.3 Archive Run Audit Object

Object: Archive_Run__c Purpose: Track each execution of the archive and delete batch jobs

Field API Name Type Description
Run Type Run_Type__c Picklist Archive or Delete
Run Start Run_Start__c DateTime Batch job start time
Run End Run_End__c DateTime Batch job end time
Records Attempted Records_Attempted__c Number Total encounters processed
Records Succeeded Records_Succeeded__c Number Successfully archived/deleted
Records Failed Records_Failed__c Number Failed records
Run Status Run_Status__c Picklist Running, Completed, Completed with Errors, Failed
Error Log Error_Log__c Long Text Area JSON or delimited error details per record
Batch Job ID Batch_Job_Id__c Text AsyncApexJob ID for traceability

3.4 Validation Rule Modification

Issue: Restrict_Modifying_Closed_Cases (and equivalent rules on Encounter Payor, Document Request, Financial Activity) will block the batch job from updating Archival_Status__c on closed encounters.

Recommended Fix: Add an exclusion clause to the Case validation rule:

AND(
  <existing closed-case restriction logic>,
  NOT(ISCHANGED(Archival_Status__c))
)

This allows Archival_Status__c to be updated on closed records while keeping all other fields protected. Apply the same pattern to child object VRs if the archival process needs to stamp child records.

4. Component 2: Archive Batch Job

4.1 Architecture

  • EncounterArchivalSchedulable — Schedulable class that launches the batch
  • EncounterArchivalBatch — Database.Batchable<SObject> that handles the archive pipeline

4.2 Batch Start (Query)

SELECT Id, CaseNumber, Subject, ClosedDate,
       (SELECT Id FROM Encounter_Payors__r),
       (SELECT Id FROM Encounter_Code_Change__r),
       (SELECT Id FROM Document_Requests__r),
       (SELECT Id FROM Tasks WHERE WhatId = :encounterId)
FROM Case
WHERE Archival_Eligible__c = TRUE
  AND Archival_Status__c = NULL
  AND RecordType.DeveloperName IN ('ARR', 'ZB')

Batch size: 10 (conservative — each record triggers subqueries + callout to Athena)

4.3 Batch Execute (per scope)

For each Encounter in the batch scope:

Step 1 — Mark In Progress

encounter.Archival_Status__c = 'Archiving In Progress';
UPDATE encounter;

Step 2 — Collect All Related Records

Query the full field set for:

Object Query Via Expected Volume
Encounter (Case) Direct — the batch record 1 per scope item
Encounter Payor Related_Encounter__c = :encounterId Low (1-5 per encounter)
Financial Activity Encounter_Payor__c IN :payorIds Medium (1-20 per payor)
Encounter Code Change Related_Encounter__c = :encounterId Low (0-10)
Document Request Related_Encounter__c = :encounterId Low (0-5)
Task WhatId = :encounterId Medium (1-50)

DECISION NEEDED: Whether to include Events, EmailMessages, FeedItem, Attachments/Files, Encounter Guidance, CaseComments. See Section 7.

Step 3 — Write to Athena

BLOCKER: Athena integration spec needed from ENG. The write mechanism determines the batch architecture:

Option Implications
REST/SOAP callout Batch must implement Database.AllowsCallouts. Max 100 callouts per execute. May need to serialize the encounter + all children into a single payload.
Platform Event Fire an event with the archive payload; ENG subscribes and writes to Athena. Decoupled but adds async complexity for verification.
Named Credential + middleware API Gateway or integration layer handles the Athena write. Cleanest separation but adds infrastructure dependency.
Big Objects (SF-native) No external dependency. Limited query capabilities but keeps data in Salesforce.

Step 4 — Verify Write

After the write, confirm:

  • Athena returned a success response (or: query Athena to confirm record count)
  • Record counts match: parent encounter + all child records sent = records confirmed in Athena
  • Each cold storage child record has OriginalEncounterId populated

Step 5 — Update Status

IF verification passed:
    encounter.Archival_Status__c = 'Archive Completed';
ELSE:
    encounter.Archival_Status__c = 'Archive Failed';
    log error to Archive_Run__c;

4.4 Batch Finish

  • Create/update the Archive_Run__c record with final counts and status
  • Optionally send a notification email or post to Chatter

5. Component 3: Delete Batch Job

5.1 Architecture

  • EncounterDeleteSchedulable — Schedulable class, runs on a separate schedule from the archive job
  • EncounterDeleteBatch — Database.Batchable<SObject>

5.2 Eligibility

SELECT Id FROM Case
WHERE Archival_Status__c = 'Archive Completed'
  AND ClosedDate <= TODAY() - 730

Recommendation: Add a 7-day buffer. Only delete records where Archive Completed was set more than 7 days ago. This gives ops time to spot-check before permanent deletion. This requires adding an Archive_Completed_Date__c field to Case, stamped when the status changes to Archive Completed.

5.3 Deletion Order

Master-Detail cascade means deleting the parent Case will automatically delete:

  • Encounter Payors (which cascades to Financial Activities)
  • Encounter Code Changes
  • Document Requests
  • Tasks, Events, EmailMessages, FeedItems, Attachments

However, for auditability, the batch should:

  1. Log the count of each child type before deletion
  2. Delete the parent Case using Database.delete() + Database.emptyRecycleBin()
  3. Record the deletion in Archive_Run__c

5.4 File Deletion Flow Coordination

Existing flow: Case_Weekly_Schedule_Closed_Delete_Files runs weekly and deletes files from closed encounters using File_Deletion_Flag__c.

Risk: If this flow runs on encounters that haven't been archived yet, the file attachments will be permanently lost — they won't exist when the archival process tries to capture them.

Recommended fix (choose one):

  • Option A: Modify the file deletion flow to skip records where Archival_Status__c is blank (not yet archived). Files are only deleted after archival is complete.
  • Option B: Ensure the archive job captures files BEFORE the file deletion flow runs. Coordinate scheduling.
  • Option C: Include file archival as part of TH-345 scope (archive files to Athena along with data).

9. Deployment Package (added 2026-04-16)

After SA-review and the integration pivot (Tim's integration pulls via REST instead of Apex writing directly to Athena), the pipeline was packaged for UAT with the following artifacts:

  • Manifest: metadata/package-th345/package.xml — 31 components, API v60.0, deploy against metadata/force-app/main/default/.
  • Component matrix: TH-345-DEPLOYMENT-COMPONENT-MATRIX.md — verified net-new vs. modified components against titan-prod on 2026-04-16.
  • UAT runbook: TH-345-FULL-COPY-RUNBOOK.html — 8-step interactive validation runbook.

Pivot notes vs. original design

  • ArchivalDataService (REST) and Archival_Config__mdt with two CMDT records were added so Tim's external integration can pull all archival data and adjust SOQL without code changes.
  • The original "EncounterArchivalBatch writes to Athena then stamps Archive Completed" flow was split: the batch now only flips status to Archiving In Progress; Tim's integration stamps Archive Completed + Archive_Completed_Date__c.
  • EncounterDeleteBatch still enforces the 7-day buffer before hard-delete.
  • Page layout and Flow modifications from the original component list are not included in this package — to be handled separately if/when required.

Deployment commands

# Dry-run
sf project deploy start --manifest metadata/package-th345/package.xml --dry-run --target-org <alias>

# Deploy + targeted tests
sf project deploy start --manifest metadata/package-th345/package.xml \
  --target-org <alias> --test-level RunSpecifiedTests \
  --tests EncounterArchivalBatchTest --tests EncounterDeleteBatchTest \
  --ignore-conflicts --wait 30

Schedulables are deployed but NOT activated in any sandbox. Prod activation is a separate cutover step (see runbook Step 8).
