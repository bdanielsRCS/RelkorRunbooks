Titan Health — Flow Order of Operations

Last updated: 2026-05-04 Scope: All 59 active flows in UAT (titan-full), the batch jobs that drive them, and how they fit into Salesforce's save order.

1. Salesforce save order — the framing

When a record is saved (Insert / Update / Upsert), Salesforce runs automation in a specific order. Where Titan Health's flows fit:

1.  Loads original record + new field values
2.  Executes system validation (required fields, FK, etc.)
3.  ▶ Executes Before-Save Flows         ← Many of our flows
4.  Executes Apex before triggers           (we have 3 — none on Case)
5.  Re-runs system validation
6.  Executes Validation Rules               ← Sprint 2 + feedback VRs run here
7.  Saves the record (no commit yet)
8.  Executes Apex after triggers
9.  ▶ Executes After-Save Flows          ← Our 3 Case after-save flows
10. Assignment / auto-response rules
11. Workflow rules
12. Processes (Process Builder)
13. Flows launched by processes
14. Escalation / entitlement rules
15. Updates Roll-up Summary fields
16. Sharing recalculation
17. Commits to database
18. Post-commit (workflow time triggers, async jobs, batch process jobs)

Key call-outs for Titan Health:

  • All Case automation runs via Flows. There are no active Apex triggers on Case today.
  • The 3 active Apex triggers are on system / packaged objects (BatchApexErrorEvent, shield_ext__Compliance_Categorization__c, KicksawEng__KicksawIntegrationLog__e) — not relevant to Case save flow.
  • When multiple before-save (or after-save) flows are configured for the same object + event, Salesforce officially says the order is "unspecified." In practice they tend to run alphabetically by API name, but don't rely on that for correctness — design each flow to be independent.

3. Scheduled flows — the daily/weekly drivers

Five active scheduled flows; each one's only job is to invoke a Batch Process Job, which in turn iterates Cases and calls a per-record auto-launched flow.

Schedule Scheduled Flow Batch Job Per-record Flow Invoked Filter
Daily 14:50 UTC Case_Scheduled_Daily_Encounters_Imported_Pending_Staging Encounters_Imported_Pending_Staging (batch size 1000) Case_Auto_launched_Imported_Pending_Staging Record_Processing_Status__c = "Imported - Pending Staging"
Weekly Case_Scheduled_Weekly_Christus_Health_ZB_RO_Batch_Job Christus_Health_ZB_RO_Batch_Job (batch size 200) RO_MASTER_Christus_Health Import_Client__c = "CHS" AND ZB RT AND Record_Processing_Status__c IN ("Staged - Pending RO Evaluation", "Requeued - Pending RO Evaluation")
Weekly Case_Scheduled_Weekly_Honor_Health_ZB_RO_Batch_Job Honor_Health_ZB_RO_Batch_Job (batch size 200) RO_MASTER_Honor_Health Import_Client__c = "HH" AND ZB RT AND same status filter
Weekly Case_Scheduled_Weekly_Northwestern_Medicine_ZB_RO_Batch_Job Northwestern_Medicine_ZB_RO_Batch_Job (batch size 200) RO_MASTER_Northwestern_Medicine Import_Client__c = "NWM" AND ZB RT AND same status filter
Weekly Sun 12 AM Account_Scheduled_Weekly_12AM_Generate_Zero_Balance_Rebill_Summaries (calls flow directly, not a batch job) Account_Auto_launched_Generate_Zero_Balance_Rebill_Summaries (per-Account run)

How the chunk size works

The batchSize (1000 for staging, 200 for RO) is the number of records processed per chunk within a single run — not a cap on records per run. A daily/weekly run processes all matching records, just in chunks for transaction-limit safety.

Once the per-record flow updates Record_Processing_Status__c away from the filter value (e.g., from "Imported - Pending Staging" → "Staged - Pending RO Evaluation"), that record is no longer picked up by subsequent runs.

8. Recurring nuance: when "order is unspecified"

Two situations to be aware of:

  1. Multiple after-save flows on Case Update — three flows fire (Auditor_Conclusion_Updates, Record_Owner_Updates, Update_Case_Fields). Salesforce does not guarantee execution order between them. If two of these flows write to the same field on the same Case, the result is non-deterministic. Audit periodically: are any of them touching the same fields?

  2. Validation Rules vs Before-Save Flows — VRs run after before-save flows but before the database write. So a VR can block a save even after a before-save flow has stamped fields. The TH-584/585/479 VRs we deployed will block invalid combinations regardless of what the before-save flows have set.

9. Operational reminders

  • Status field that drives everything: Case.Record_Processing_Status__c. Values include "Imported - Pending Staging", "Staged - Pending RO Evaluation", "Requeued - Pending RO Evaluation", and end states. The whole pipeline is gated by this field.
  • Error routing: the staging flow's no-Account-match path routes Cases to the ZB_Encounter_Staging_Error_Queue queue — periodically check that queue for stuck records.
  • Adding a new Honor Health / Northwestern / Christus RO code: create a new RO_<code> flow following the pattern, then add a branch in the corresponding RO_MASTER_* flow to dispatch to it.
  • Adding a new client: a new client requires (1) a new RO_MASTER_<Client> flow, (2) a new BatchProcessJobDefinition referencing it, (3) a new Case_Scheduled_Weekly_<Client>_ZB_RO_Batch_Job scheduled flow.
